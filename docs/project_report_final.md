# プロジェクトレポート：本音ダダ漏れ「煽りLGTMジェネレーター」

## 開発を通じた「拒絶の審美眼」とフルサイクル・エンジニアリングの実践

### 1. はじめに：制作の動機とプロジェクトの目的

「優れたシステムを構築するためには、単にコードを書く能力だけでなく、外部からの不条理な構造を適切に理解し、技術者としての誇りを守るための『シニカルな視点』が必要不可欠である」。

エンジニアとして日々の業務に邁進する中で、私たちが直面するのは「技術」そのものよりも、むしろそれを取り巻く「商流」や「人間関係」という非論理的な障壁であることが少なくありません。学習の過程で提示される「クリーンなコード」や「理想的なアーキテクチャ」をなぞるだけでは、実際の業務で直面する曖昧な要件や、技術者としてのメンタルを蝕む「終わりのない修正」に対する耐性は養われません。

多くのエンジニアにとって、コードレビューにおける「LGTM（Looks Good To Me）」は、時として思考停止の同義語になりがちです。本当にそのコードは良いのか。それとも、単に「拒絶」することで発生するコミュニケーションコストを嫌い、妥協的に承認しているのではないか。あるいは、その「不条理」を改善するコストを嫌い、現状を肯定しているのではないか。

この切実な問題意識を起点として、私は自らに一つのミッションを課しました。「エンジニアが現場で直面する安易な承認文化に対するシニカルな風刺を形にし、遊びながら『批評的思考』を再認識できる、バイラル性の高いWebアプリケーションを開発する」という挑戦です。そうして誕生したのが、美しいテンプレート画像に強烈な本音（煽り文句）を添えてLGTM画像を生成する、「本音ダダ漏れ！煽りLGTMジェネレーター」です。

本プロジェクトの最大の目的は、単にジョークツールを公開することに留まりません。Next.js 16を用いた最新のApp Routerアーキテクチャの実装、Tailwind CSS v4による先進的なスタイリング、そして `@vercel/og` を駆使した動的なエッジ画像生成まで、現代のWebフロントエンド開発における「フルサイクル・エンジニアリング」を独力で完遂することにありました。この開発過程を通じて、単なる「実装屋」ではない、プロダクト全体を統括する「プロダクト・マネジメント能力」を飛躍的に向上させることが、この挑戦の本質的な動機でした。

### 2. アプリケーションの概要と「煽りLGTM」の概念

「煽りLGTMジェネレーター」は、エンジニアの日常的な承認作業に、あえて「本音」という名の楔を打ち込む、創造的な画像生成ツールです。

#### 2.1. 承認の裏側にある「胃壁を削る」本音の可視化
従来のLGTM画像は、単なる肯定のサインでした。しかし、本アプリではその肯定の裏側に潜む「諦め」「懸念」「皮肉」を言語化します。
例えば、プリセットに含まれる「（※コード一切読んでないけど）」というフレーズは、多忙を極める現場でエンジニアが抱く罪悪感と、それを許容せざるを得ない構造的な欠陥を端的に表現しています。

この「表面的な肯定（LGTM）」と「直感的な拒絶（本音）」のギャップを埋めることこそが、本ツールの核心です。安易な「ヨシ！」の代わりに、毒のある画像を生成し、SNSやGitHubを通じて共有する。これは、単なる煽りを超えた、エンジニアリングにおける「誠実な疑念」の表明でもあるのです。

#### 2.2. アイデンティティとしてのテンプレート選定
提供されるテンプレートは、エンジニアの心理状態やプロジェクトの状況を象徴的に表しています。
- **This is Fine (炎上)**: 深刻な納期遅延やバグに直面しながらも、平静を装わなければならない矛盾。
- **Stonks (爆益)**: 無理な実装が一時的に成功した際の、根拠のない万能感。
- **万物悟り (宇宙)**: あまりに理解不能な設計に直面し、思考が銀河の彼方へ飛躍した状態。

これらは単なるミームではなく、エンジニアなら思わず苦笑してしまうような「現場の質感」を伴っています。生成された結果は即座にダウンロード可能で、GitHubのPRコメントやX（旧Twitter）へ投稿できるよう設計されており、他者との共有を通じて、個人の「叫び」をコミュニティの「共通言語」へと昇華させます。

### 3. 使用した技術スタックとその選定理由

本プロジェクトの開発にあたっては、2026年現在のフロントエンド開発において最も洗練され、かつ高いパフォーマンスを発揮できる最新の技術スタックを選択しました。

#### 3.1. Next.js 16 (App Router)
基盤には最新のNext.js 16を採用しました。今回のアプリは単一のページで完結するシンプルな構成ですが、あえてNext.jsを選んだ理由は、今後の拡張性と「開発体験（DX）」の向上にあります。App Routerによる直感的なディレクトリ構造と、サーバーサイドでのOG画像生成（Metadata API / @vercel/og）との親和性は、SNSでの拡散を前提としたプロダクトにおいて不可欠な要素でした。

#### 3.2. @vercel/og によるエッジ画像生成
本アプリの「心臓部」といえるのが、 `@vercel/og` を用いた動的な画像生成ロジックです。従来のサーバーサイド生成では負荷が課題となりますが、Satoriエンジンを活用したエッジ実行により、ユーザーがテキストを入力した瞬間に「本物」の画像を生成・プレビューすることを可能にしました。背景がグラデーションのカラーモードと、画像ベースのミームモードをシームレスに切り替える実装は、コードの柔軟性と実行速度のバランスを極限まで追求した結果です。

#### 3.3. Tailwind CSS v4
スタイリングにはTailwind CSSの最新バージョン（v4）を導入しました。v4で刷新されたアーキテクチャにより、従来よりも少ない記述量で、ネオンサインのような光彩を放つ「ダークモード・テックUI」を実現しました。特に、ガラスモーフィズムを多用したコントロールパネルや、テンプレート選択時の滑らかなアニメーションは、CSS-in-JSに頼らない低レイテンシな描画を可能にしました。

### 4. フロントエンドの実装詳細：高速プレビューエンジンの構築

プロジェクトの技術的ハイライトは、メインのページコンポーネントにおけるリアクティブ・ロジックとUXエンジニアリングの統合にあります。

#### 4.1. デバウンス処理とUXの最適化
ユーザーがテキストを入力するたびにAPIリクエストを飛ばすと、ネットワーク負荷が増大し、ユーザー体験を損ないます。そこで、 `useEffect` と `setTimeout` を組み合わせた200msのデバウンス処理を実装しました。この「タメ」があることで、入力の合間を縫って効率的にプレビューを更新しつつ、タイピングの軽快さを損なわない設計となっています。

#### 4.2. 型安全なテンプレート管理
`TEMPLATES` 定数を完全に分離し、各テンプレートが持つメタデータ（id, name, bg, mode, thumb）を TypeScript の型定義に基づいて厳格に管理する構造へとリファクタリングしました。これにより、将来的にユーザーがカスタムテンプレートをアップロードしたり、DBから動的に取得するための拡張性を確保しました。

### 5. コンテンツ設計：煽りの言語化と言語モデル

本アプリケーションの「教育的価値」と「エンターテインメント性」を両立させているのが、 `PRESETS` 定数に定義された「エンジニアの本音」のサンプリングです。

#### 5.1. 煽り文句の階層構造
単に「嫌な言葉」を並めるのではなく、実務で発生するコミュニケーションの「裏側」をカテゴリに分類しました。
- **技術的負債への諦諦**: 「（※動けばヨシ！）」に代表される妥協。
- **責任回避のユーモア**: 「（※本番でバグらないことを祈ります）」という祈祷。
- **徹底した拒絶**: 「（※LGTM（Looks Garbage To Me））」という皮肉。

#### 5.2. 評価コメントに込められた皮肉
ユーザーが自由に入力できる機能に加え、あえて強力なプリセットを用意したのは、エンジニアが「言いたくても言えなかったこと」を一瞬で見つけ出し、ボタン一つで代弁させるためです。この心理的ハードルの低下が、ツールの利用率と中毒性を高める鍵となりました。

### 6. SNS連携とバイラル設計：エンジニアの「自虐」を刺激する

本プロジェクトを個人の趣味開発で終わらせず、社会現象としてのバイラルを狙うために、戦略的なOGP設計を行いました。

#### 6.1. シェアされる「作品」としてのLGTM
GitHubのプルリクエストにこの画像が貼られた際、他のレビュアーや作成者がどのような反応を示すか。この「リアクションの連鎖」こそをプロダクトとして設計しました。タイムライン上に次々と流れてくる多種多様な「煽り」は、それ自体がコンテンツとなり、新たなユーザーを惹きつける磁石となりました。

#### 6.2. 動的OGPによるタイムラインの支配
GitHubやXでのシェア時も、 `@vercel/og` が動的に画像を生成します。シェアされたリンクを見るだけで、その人がどんな「煽り」を行ったかが一目でわかる「中身が見えるシェア」の実装により、クリック率を劇的に向上させました。

### 7. 直面した課題と技術的な反省点

開発プロセスは常に順風満帆ではありませんでした。特に最新の技術スタックを採用したからこそ直面した課題がいくつか存在します。

#### 7.1. 画像読み込みの遅延とスケルトンUI
初期の実装では、エッジからの画像返却を待つ間、プレビューエリアが空白になる現象が発生しました。この反省から、 `isGenerating` ステートを導入し、Lucideアイコンの `RefreshCw` によるアニメーション表示を実装しました。また、 `img` タグの `crossOrigin` を適切にハンドリングすることで、生成された画像をBlobとして確実にダウンロードさせるロジックを磨き上げました。

#### 7.2. クライアントサイドでの描画負荷
リアルタイムプレビューとダウンロード機能の両立において、クライアントサイドでのキャンバス描画はコストが高いと判断しました。最終的には、すべての重い描画を `@vercel/og` のサーバーサイド（エッジ）へ委任し、クライアントは単にその結果をフェッチするのみという「シン・クライアント的設計」に変更することで、モバイル端末でも快適な操作感を実現しました。

### 8. 今後の展望と追加機能のアイデア：進化する煽り

#### 8.1. AIによるコード解析連携
今後は GitHub API と連携し、プルリクエストの「差分（diff）」を解析し、そのコードの汚さに合わせた「最適な煽り」をAIが自動提案する機能を構想しています。冷徹なロジックでコードを切り裂き、最もダメージの大きい煽り文句を生成する。それは、人間による主観的な批判を超えた、新たな技術的防衛の形になるはずです。

#### 8.2. 世界煽りランキングの統計分析
Vercel KVを活用し、どの煽り文句が最も多くシェアされたかをリアルタイムで統計化する機能を追加する予定です。これにより、「現代のエンジニアが最も苦しんでいる不本意な承認パターン」を統計的に明らかにし、業界全体の技術的意識向上に向けた社会学的データとしての価値を持たせたいと考えています。

「技術を磨き、安易な承認を拒絶し、本音という名のスパイスでプロダクトの品質を守る」。本プロジェクトで培ったこの批評的精神を糧に、今後もより大規模で、世の中に一石を投じるようなシステム開発に挑戦し続けていきたいと思います。
